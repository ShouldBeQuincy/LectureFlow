# 扩展的上限 / Extension limits

[简体中文](#简体中文) · [English](#english)

## 简体中文

给维护者和对策文件贡献者看：浏览器扩展对“页面给了多少东西”设了哪些上限、超过时怎么做。所有上限都远高于正常的讲座页（几条到几十条轨道；清单几 KB 到几 MB；长讲座的 HLS 播放列表可以有几千到三万个分片），只有异常或恶意的页面才会碰到。改动任何一个数值都要同时改钉住它的单元测试，并更新本表。

### 每次探测

| 常量（文件） | 数值 | 超过时 |
|---|---|---|
| `LIMITS.manifests`（`src/lib/detect.js`） | 12 份清单 | 其余的列为“清单读不到”的轨道，不去读 |
| `LIMITS.probes` | 8 份媒体播放列表 | 不再为时长和 DRM 信号去读 |
| `LIMITS.files` | 8 个文件 | 不再为大小和类型去探测 |
| `LIMITS.urlBytes` | 48 Mi 字符 | 所有清单合计能解析出的地址；用完后分片地址不再解析（它们本来就按分片处理） |
| `LIMITS.urlLength` | 8192 字符 | 页面给出的地址（媒体元素及其 `<source>`、资源记录、请求记录、嵌入帧）更长时不收：资源记录、请求记录、嵌入帧整条不收，媒体元素只去掉这个地址（时长与 MediaKeys 仍然算数）。嵌入帧的地址去掉 `#` 片段后再判断长度、计入 `scanChars` 并保存（片段不会发往服务器，用到帧地址的地方也都不看片段）；本次探测所在的帧（页面内按钮的那一帧）与顶层帧不论地址多长都收下。探测按“去掉 `#` 片段后”的地址建候选，那样算更长的同样不收。依据：超过 8 KB 的请求，nginx、Apache 的默认设置与 CloudFront 都会拒绝，真实页面碰不到；与 `MAX_MANIFEST_URL_LENGTH` 相同；V8 对不超过 16383 字符的字符串按内容算哈希，以地址为键的表（候选合并、轨道去重、MediaKeys 地址）因此保持线性（SEC28b 中-4：1000 个 16400 字符、只在末尾不同的地址，改动前 2.5 s） |
| `LIMITS.frames` | 128 个帧 | 一次扫描收下的帧。本次探测所在的帧与顶层帧总是收下；其余先收“像媒体”的帧（有带地址的媒体元素，或有名字像清单 / 媒体文件的资源记录），再收有内容的，最后是空帧，各按扫描顺序（SEC33 低-2：排在前面的空帧、只有非媒体内容的帧挤不掉播放器帧；127 个“像媒体”的帧仍然可以把它挤出上限，信-8）。输出仍按扫描顺序 |
| `LIMITS.elements` | 1000 个 | 所有帧合计的媒体元素，按下面 `scanChars` 一行的先后收；其余不收 |
| `LIMITS.sources` | 16 个 | 一个媒体元素的 `<source>` 子元素，其余不收 |
| `LIMITS.resources` | 10000 条 | 所有帧合计的资源记录（扫描本来每帧最多取 2000 条），先后同上 |
| `LIMITS.scanChars` | 16 Mi 字符 | 嵌入帧的地址与各帧内容合计能带的地址字符数（本次探测所在的帧与顶层帧自己的地址不计，请求记录另有额度）。先扣挑帧时收下的其他嵌入帧的地址（去掉片段后，最多 127 × 8192 ≈ 1 Mi）；然后收各帧的内容。每个帧把自己的内容按“证据强弱”分五档：① 名字像 HLS / DASH 清单的资源记录；② 正在播放（有 `currentSrc`）的媒体元素；③ 名字像音视频文件的资源记录；④ 其他带地址的媒体元素；⑤ 其余（别的资源记录、没有地址的元素）。所有帧的①–④（证据）先收，⑤ 最后收；两部分里都是**各帧轮流**（SEC33d 低-6）：每一圈每个帧交出自己剩下的最强的一条，这一圈的条目按档次先后收，同一档按帧的顺序（本次探测所在的帧、顶层帧在前，其余按扫描顺序）。所以任何一个帧（顶层帧也一样）都要等其他每个帧各收过一条才能收第二条，没有地址的媒体元素、非媒体的资源记录和空帧挤不掉别的帧的证据（SEC33 低-2）。一条按地址字符付费（SEC36 低-8）：地址合计超过 `urlLength` 的元素（例如带 16 个长 `<source>` 的），每多 `urlLength` 个字符，它所在的队列（帧自己的文档，或下面说的一个子文档）就先等一圈。扫描还会读进与帧同源的子帧（`scanFrame` 的 `doc` > 0），这些条目进的是父帧自己的列表：一个帧的各圈在它自己的文档与这些子文档之间交替（子文档之间再轮流；SEC36 低-7）；长地址元素的等候记在各自的队列上，等候的那一圈算这一边用掉，下一圈让给另一边（SEC36b 低-11、SEC37 低-13）。所以每个帧（不论有没有子文档）平均每圈最多占约 8 KB；子文档里的垃圾（长地址元素也一样）最多占父帧一半的圈；父帧自己文档的条目一圈就够时至少每两圈出一条，本身要等 t 圈的条目最迟在上一条之后 2t 圈出（没有子文档时 t 圈）。已知取舍：自己的条目本身超过 8 KB（例如带几个签名 `<source>` 的元素）而帧里又有同源子文档时，它要多等一倍（SEC37 复核者的 `own-long-kids-m3u8` 形状，安全条数 4 → 2）；换来的是普通讲座（每条不超过 8 KB）的最坏情况更好。`doc` 只用于这里，收完就去掉，不进入探测与报告。于是要挤掉某个帧自己文档的前 n 条证据，其余各帧得一起填满约 n 圈（这个帧里有同源子文档时约 2n 圈）；按 128 个帧、每帧每圈约 8 KB 算，16 Mi 约是 16 圈：前十几条（有同源子文档时前八条左右）是安全的，再往后不保证。不论垃圾在顶层页（信-8）、单独扫描的嵌入帧（跨源而站点已授权；低-6）还是同源子帧里都如此；实测 SEC33d 的 `embedexact`、`m3u8exact`，SEC36 的“≥115 个帧各交一个 18 个长地址的元素”与“同源小部件”形状都不再丢轨道。仍然做得到的：127 个“像媒体”的帧把播放器帧挤出 128 帧的上限（帧数上限，见上）。页面内按钮只扫一帧，不受这些挤占影响。放不下的地址照上面的办法不收。“像清单 / 文件”（`scanHint`，不解析地址，只决定先后，不影响探测结果）按探测本身对资源记录的分类来判断：地址最后一段的扩展名（与 `classifyUrl` 的读法相同）、路径里的 Azure 式 `manifest(format=…)`（编码过的也算）、由媒体元素加载；响应失败（状态 400 以上）的记录永远不算。所以它不会把探测认作清单或媒体文件的记录排到后面。没有扩展名的清单地址在资源记录里排在 ⑤：资源记录不带 Content-Type，探测本身也认不出它，能认出它的只有浏览器的请求记录，而请求记录另有额度 |
| `LIMITS.requestChars` | 4 Mi 字符 | 请求记录（浏览器自己看到的媒体与清单响应，最可靠的证据）单独的额度，不与页面内容争（SEC33 低-2）；`requests.js` 记录时就守着它（AUD3 中-2）：地址超过 `LIMITS.urlLength` 的响应根本不记，`Content-Type` 只留前 256 个字符，每个标签页最多 300 条、地址合计不超过本额度（300 × 8192 ≈ 2.4 Mi，所以这一层实际碰不到）；每个响应按地址查表，不重读已记的地址 |
| `LIMITS.attrLength` | 256 字符 | `<source>` 的 `type` 更长时当作没写（同 `HLS_LIMITS.attrLength`）；选择器读值里各节点的标签名、`id`、每个 class 截到这个长度（报告本来只留 64 字符，所以报告不变）。计入报告的 `limits.longValues` |
| `LIMITS.attrNames` | 32 个 | 选择器读值里一个节点的属性名只留前 32 个（报告本来只留 32 个），其余计入 `limits.longValues` |
| `LIMITS.fileTracks` | 1000 条 | 单文件轨道：先收任意媒体元素引用的（`src`、`currentSrc` 或某个 `<source>`，不论是否正在播放），再收其余的，两组各按地址顺序；其余不列出。只影响超过上限的页面，读大小与类型的 8 次探测照旧 |
| `MAX_MANIFEST_URL_LENGTH`（`detect.js`） | 8192 字符 | 清单地址更长时整份跳过，不读（`LIMITS.urlLength` 已先把它拿掉） |
| `MAX_MANIFEST_BYTES`（`src/lib/bgfetch.js`） | 2 MiB | 清单只读这么多，超过算读取失败 |
| `HLS_LIMITS`（`src/lib/hls.js`） | 变体 256、音轨等 256、分片 30000、`#EXT-X-MAP` 256、地址长度 4096、每份 16 Mi 字符 | 多出的部分不收，静默截断 |
| `HLS_LIMITS.attrLength` | 256 字符 | 轨道保留的属性值（`CODECS`、`NAME`、`LANGUAGE`、`GROUP-ID`、`CHANNELS`，以及与之对应的 `AUDIO`、`VIDEO`）。更长的当作没写，不截断：截掉一半的编解码器列表或名字看起来像真的 |
| `TEMPLATE_LIMITS`（`src/lib/dash.js`） | 14 项，见源码注释；每份 MPD 16 Mi 字符 | 同上 |
| `TEMPLATE_LIMITS.attrLength` | 256 字符 | `codecs`、Representation 的 `id` 更长时当作没写（Representation 自己的 `codecs` 过长时也不改用 AdaptationSet 的）；`lang` 更长的 AdaptationSet 不作为轨道提供，因为 `lang` 是轨道选择符的一部分，LectureFlow 按清单原样匹配 |
| `MAX_TESTS_PER_RULE`（`src/lib/profile.js`） | 每条轨道规则 256 个地址 | 其余轨道不再拿来匹配这条规则 |

### 探测之后：后台保存什么、卡片显示什么（`RETAIN_LIMITS`，`src/lib/retain.js`）

探测结果只在内存里：每个标签页的顶层探测一份，页面内按钮（嵌入帧）的探测各一份（每个标签页最多 `frameResults` 份）。标签页关闭、跳到别的地址时丢弃；浏览器停用扩展后台时（Chrome 的 service worker、Firefox 的事件页空闲后）也一起消失。

| 常量 | 数值 | 作用与超过时 |
|---|---|---|
| `tracksShown` | 200 条 | 弹窗、页面内卡片、确认窗口最多列出这么多轨道。先列“主要音视频 / 双机位 / 仅音频”三个选择要用的轨道（按全部轨道算），再按原顺序补满；其余的不列出、不能勾选、不能发送，列表下面写“还有 N 条轨道未显示”（`tracksHidden`）。标题里的条数、受保护条数、工具栏图标上的数字仍按全部轨道算。“允许读取 Cookie 的网站”只列出显示的轨道所在的网站 |
| `tracksKept` | 1000 条 | 后台保存的轨道总数。按同样的办法挑（先是显示的那些，所以显示与可发送的轨道和不设上限时完全一样），其余放弃，计入“还有 N 条轨道未显示”；标题与图标上的条数仍按全部轨道算。导出的报告在 `limits.tracks` 里写放弃了几条（这种报告回放出的轨道会比 `expected` 多） |
| `textChars` | 512 Ki 字符 | 探测报告收录一份清单原文的上限（`src/lib/report.js` 同一个值）。更长的原文报告本来就不收（`truncated`），所以后台也不保存 |
| `tabTextChars` | 8 Mi 字符 | 一个标签页为探测报告保存的清单原文合计。按读取顺序保存，放不下的标为 `truncated`（报告里同样标出）。页面内按钮的探测不生成报告，一份原文也不存 |
| `totalTextChars` | 32 Mi 字符 | 所有标签页合计。超过时，先由刚存进来的那个标签页自己的其他探测放弃原文，再由其余探测按占用从大到小放弃（一样大的先放弃早的；SEC36 低-10：几个大页面挤不掉更早的小标签页），不放弃轨道；之后为那个标签页导出报告会重新探测一次 |
| `totalScanChars` | 64 Mi 字符 | 所有探测为报告保存的扫描结果（`raw.frames`、`raw.webRequests`）合计的地址字符数（帧地址、媒体元素及其 `<source>`、资源记录、请求记录；一份最多约 16 + 4 Mi，另加页面自己的地址）。只有标签页的顶层探测保存扫描结果，页面内按钮的探测不生成报告，不保存。超过时按与 `totalTextChars` 相同的先后（占用大的先）放弃扫描结果，连同原文一起（反正它的报告要重新探测），不放弃轨道 |
| `frameResults` | 16 份 | 一个标签页保存的页面内按钮探测（每个用过页面内卡片的帧一份）。超过时最早的一份被忘掉：那张卡片重新打开时重新探测；已经开着的卡片点发送会得到“页面已经变了”，要关掉重开 |

字符数：V8 把纯 ASCII 的文本按每字符 1 字节存，其他文本 2 字节。上面三个原文额度只管**清单原文**（`fetches[].text`）：原文最坏每个标签页约 16 MiB、所有标签页合计约 64 MiB（以前每个标签页最坏 40–80 MiB，标签页数不限）。它们不是后台常驻内存的总上限，下面几样不在额度之内：

- **轨道**（地址、变体、名字）：显示的轨道总是保存、永远可以发送；连同未显示的最多 `tracksKept` 条。文件轨道最多 `LIMITS.fileTracks` 条、地址最长 `LIMITS.urlLength`；来自清单的轨道还受上一节的探测上限约束（每条 DASH 轨道的 id 都含整个清单地址，最长 8 KB）。
- **扫描结果**（`raw.frames`、`raw.webRequests`，报告用）：保存的就是探测用的那份，已经按上一节的 `LIMITS.frames` / `elements` / `sources` / `resources` / `urlLength` / `scanChars` / `requestChars` 收过：帧与内容的地址合计最多 16 Mi 字符，请求记录另有最多 4 Mi（实际不超过约 2.4 Mi），另加本次探测所在的帧与顶层帧自己的地址（不计入额度，长度也不限；顶层帧地址就是标签页的地址）。页面响应里观察到的值（`observed`）有自己的上限（`src/lib/observe.js`：每个字符串 2048 字符，`*` 最多 16 个值）。
- **探测结果里只在探测时用的部分不再保存**（SEC33 低-3）：`ignored`（所有非媒体地址的列表）不存；`segmentRuns` 只存各段的个数（`count`，报告只用它），不存地址模板；`evidence` 只存四个布尔值（`mse`、`mediaKeys`、`mediaKeysOnStream`、`encrypted`，报告只用它们），带 MediaKeys 的地址与各元素的时长在探测时已经用过，不存（SEC33 低-5）。探测函数本身（以及对策文件 CI 的回放）照旧返回完整的两项。
- `<source>` 的 `type` 与选择器读值（`reads`）的节点受 `LIMITS.attrLength` / `attrNames` 约束（见上表）；读到的值本身扫描时截到 1000 字符，每个选择器最多 3 个节点、每个节点的路径最多 8 层、每层最多 8 个 class。
- 弹窗用来建议授权的读不到的嵌入帧地址（`opaque`，最多 20 个）：超过 `LIMITS.urlLength` 的去掉 `#` 片段，仍然超过就不收（计入 `limits.longUrls`）；用到它的地方只看主机与路径。
- 所有标签页合计：清单原文 `totalTextChars`、扫描结果 `totalScanChars`；页面内按钮的探测每个标签页最多 `frameResults` 份（见上表）。
- 探测途中嵌入帧换了文档（顶层探测）：不再向它请求，只来自它的轨道去掉，其余照常保存（SEC36 低-9）。已知不足（低-12）：它给出的清单如果把别的帧的地址当作分片“吸收”了，这些地址也随那条轨道一起不再列出。
- **目前仍不受上限约束**的：页面内按钮所在的帧与顶层帧自己的地址（见上，浏览器允许到约 2 MB；它就是页面的地址，探测、对策文件匹配与报告都要用，不能截短）；轨道（每次探测最多 `tracksKept` 条，地址见第一条）没有跨标签页的合计，标签页数由用户决定。
- 实测，改动前 → 改动后（作者的探针，Node，一次探测走一遍“收扫描 → 探测 → 留轨道 → 复制”，GC 后的常驻量）：
  - 2000 条 8192 字符的文件地址：49.2 MiB、196 ms → 32.6 MiB、185 ms；
  - 4000 个带 8000 字符地址的媒体元素：126.6 MiB、270 ms → 31.9 MiB、58 ms；
  - 20 个帧各 2000 条 1000 字符的地址：146.1 MiB、682 ms → 13.3 MiB、147 ms；
  - 1000 条 16400 字符、只在末尾不同的地址：63.9 MiB、2486 ms → 0.2 MiB、1 ms。
- 最坏情形（SEC33 复核者的探针 `mem.mjs`，整个 `detectTab`，GC 后、页面输入已释放；“之前”是 SEC33 复核时的实测，“之后”是作者 C130 用同一探针在去掉 `ignored`、分片模板并限制 `type` / `reads` 之后重量的）：
  - 10000 条互不相同的非媒体地址，恰好约 16 Mi 字符：37.4 → 20.1 MiB、0 条轨道；
  - 同样规模的三个一组分片：43.2 → 20.5 MiB；
  - 1000 个元素 × 16 个 `<source>`、`type` 512 字符：29.9 → 21.9 MiB（`type` 9 字符时 22.3 MiB）；
  - 选择器读值节点的 `id` / `classes` 2048 字符、各 1000 个属性名：8.5 → 6.6 MiB（读值节点 4.75 → 0.46 Mi 字符）；
  - 1000 个元素、8192 字符文件地址：27.3 → 27.2 MiB（不变：扫描 15.6 Mi + 文件轨道地址 7.8 Mi 字符）；
  - 1000 个带 MediaKeys 的元素 × 16 个 1 Ki 字符的 `<source>`（SEC33d 复核的 `keys` 形状）：37.1 → 21.9 MiB（`mediaKeysUrls` 15.9 Mi 字符不再保存；作者 C130 用同一探针在去掉它之前、之后各量一次）。
- 按上限推算：每个标签页一次探测约为扫描 16 + 请求记录约 2.4 + 文件轨道地址 8 + DASH 轨道 id 8，约 35 Mi 字符，再加清单原文额度 8 Mi、读值节点（每个节点最多约 28 K 字符：8 层 × 标签、`id`、8 个 class 各 256，加 32 个属性名各 256），以及上一条里不受限的几项。
- 超过任何一个上限时，导出的报告多一个 `limits` 对象，写明各项不收了多少（`frames`、`elements`、`sources`、`resources`、`webRequests`、`longUrls`、`scanChars`、`longValues`、`fileTracks`、`tracks`）；都没超过时报告里没有这一项，与以前完全相同。
- **页面内列表取得的讲座信息**（`main.js` 的 `sessions`）只有 30 分钟有效期（读取时检查），没有条数上限；每条只含观察值组成的几条命名轨道，条数随用户的批量发送增长：确认窗口里的批量发送每批最多 500 行，页面内的批量卡片逐节加载，没有这个上限。

保存前，后台把探测结果复制一份（`detachedCopy`）：解析器从清单里取出的字符串（例如 `CODECS` 的值）在 V8 里可能引用整份原文，不复制的话，放弃的原文仍然留在内存里。复制按字符串**去重**：同一个字符串无论被多少处引用都只复制一次，原本共用的对象复制后仍然共用。例外是超过 16383 字符（`DEDUP_MAX_LENGTH`）的字符串：V8 对这么长的字符串只按长度算哈希，很多等长的长字符串会让去重表退化成逐一比较（SEC28b 中-3），所以它们不去重，每处引用各复制一份。`structuredClone` 会给每一处引用各复制一份，一个被 2000 个 Representation 共用的值就会变成 2000 份（SEC28 高-1）。复制的时间与额外内存都与“不同字符串的总长度加对象个数”成正比：最坏形状（全部字符串互不相同，3072 条轨道、30 Mi 字符）实测 106 ms，复制本身约 55 MiB。

## English

For maintainers and profile contributors: the limits the browser extension puts on what a page gives it, and what happens past them. Every limit is far above a real lecture page (a few to a few dozen tracks; manifests of a few KB to a few MB; the HLS playlist of a long lecture can have thousands to 30,000 segments), so only an unusual or hostile page reaches one. Changing a value means changing the unit test that pins it, and this table.

### Per detection

| Constant (file) | Value | Past it |
|---|---|---|
| `LIMITS.manifests` (`src/lib/detect.js`) | 12 manifests | the rest are listed as "playlist unreadable" tracks, not read |
| `LIMITS.probes` | 8 media playlists | no more read for duration and DRM signals |
| `LIMITS.files` | 8 files | no more probed for size and type |
| `LIMITS.urlBytes` | 48 Mi characters | addresses all manifests together may resolve; past it, segment addresses are not resolved (they are segments anyway) |
| `LIMITS.urlLength` | 8192 characters | a longer address the page gives (a media element's or its `<source>`'s, a resource entry's, a request's, an embedded frame's) is left out: the resource entry, request or frame entirely, a media element only loses that address (its duration and MediaKeys still count). An embedded frame's address loses its `#` fragment before it is measured, charged to `scanChars` and kept (a fragment never reaches a server, and nothing that reads a frame's address looks at it); the frame detection runs in (an in-page button's) and the top frame stay however long their addresses are. Detection keys candidates by the address without its `#` fragment, and leaves out one that is longer that way too. Why: most servers and CDNs refuse a request past 8 KB (nginx and Apache by default, CloudFront), so a real page never reaches it; it equals `MAX_MANIFEST_URL_LENGTH`; and V8 hashes a string of up to 16383 characters by its contents, so the tables keyed by address (merging candidates, deduplicating tracks, MediaKeys addresses) stay linear (SEC28b 中-4: 1000 addresses of 16400 characters differing only at the end took 2.5 s before) |
| `LIMITS.frames` | 128 frames | frames one scan takes. The frame detection runs in and the top frame always; of the others, first those that look like media (a media element with an address, or a resource entry named like a manifest or media file), then those with anything in them, then the empty ones, each in scan order (SEC33 低-2: empty frames and frames with only non-media content listed first cannot push out a player frame; 127 frames that look like media still can, 信-8). The output stays in scan order |
| `LIMITS.elements` | 1000 | media elements of all frames together, taken in the order given under `scanChars` |
| `LIMITS.sources` | 16 | `<source>` children of one media element |
| `LIMITS.resources` | 10000 entries | resource entries of all frames together (the scan already takes at most 2000 a frame), in the same order |
| `LIMITS.scanChars` | 16 Mi characters | address characters the embedded frames and the frames' contents may hold together (not counting the addresses of the frame detection runs in and of the top frame; the requests have their own allowance). First the addresses of the other embedded frames as they are picked (without fragments, at most 127 × 8192 ≈ 1 Mi); then the frames' contents. Each frame sorts its own into five tiers by strength of evidence: ① resource entries named like HLS / DASH manifests; ② media elements playing something (`currentSrc`); ③ resource entries named like audio or video files; ④ other media elements with an address; ⑤ the rest (other resource entries, elements without an address). Tiers ①–④ (evidence) of every frame come before ⑤ of any; in both parts **the frames take turns** (SEC33d 低-6): each turn every frame offers its strongest entry left, and the turn's entries are taken strongest tier first, those of one tier in frame order (the frame detection runs in and the top frame first, the others in scan order). So no frame, the top one included, takes a second entry before every other frame had a first, and media elements without an address, non-media resource entries and empty frames cannot push out another frame's evidence (SEC33 低-2). An entry pays by its address characters (SEC36 低-8): for an element whose addresses add up to more than `urlLength` (one with 16 long `<source>`s, say), its queue (the frame's own document, or one of the child documents below) first waits a turn for each further `urlLength`. The scan also reads a frame's same-origin child frames (`scanFrame`'s `doc` > 0) into the frame's own lists: a frame's turns alternate between its own document and those child documents (which take turns among themselves; SEC36 低-7); a long element's wait is kept on its own queue, and a turn spent waiting counts as that side's, the next turn going to the other side (SEC36b 低-11, SEC37 低-13). So every frame, with child documents or without, takes about 8 KB a turn on average at most; junk in a child document (long elements too) gets half of its parent's turns at most; and an entry of the parent's own document that needs one turn comes at least every other turn, one that itself waits t turns at most 2t turns after the one before (t without child documents). A known trade-off: an entry of the frame's own that is itself over 8 KB (an element with a few signed `<source>`s, say) waits twice as long when the frame has same-origin child documents (the SEC37 reviewer's `own-long-kids-m3u8` shape: 4 safe entries → 2); in exchange, the worst case of an ordinary lecture (no entry over 8 KB) is better. `doc` serves only this and is removed right after; it reaches neither detection nor the report. So crowding out the first n entries of evidence of a frame's own document takes all the other frames filling about n turns (about 2n with same-origin child documents in that frame); at 128 frames and about 8 KB a frame a turn, 16 Mi is about 16 turns: the first dozen or so entries (about eight with child documents) are safe, beyond that nothing is promised. That holds whether the junk is on the top page (信-8), in a separately scanned embedded frame (cross-origin on a site the user granted; 低-6) or in a same-origin child frame; measured: the SEC33d shapes `embedexact` and `m3u8exact` and the SEC36 shapes "115 or more frames each offering an element of 18 long addresses" and "same-origin widget" no longer lose tracks. Still possible: 127 frames that look like media push a player frame out of the 128-frame limit (the frame count, above). An in-page button scans one frame and is affected by none of this. An address that no longer fits is left out as above. "Named like" (`scanHint`, no URL parsing; it decides the order only, never what detection makes of an entry) follows how detection itself classifies a resource entry: the extension of the address's last path segment (read as `classifyUrl` reads it), an Azure-style `manifest(format=…)` in the path (percent-encoded too), loaded by a media element; an entry whose response failed (status 400 or more) never counts. So it never puts behind an entry detection takes for a manifest or media file. A manifest address without an extension ranks ⑤ among resource entries: an entry carries no Content-Type, so detection cannot tell it either; only the browser's request records can, and they have their own allowance |
| `LIMITS.requestChars` | 4 Mi characters | an allowance of its own for the request records (the media and manifest responses the browser itself saw, the most reliable evidence), never contended by page content (SEC33 低-2); `requests.js` holds to it as it records (AUD3 中-2): a response whose address is longer than `LIMITS.urlLength` is not recorded at all, a `Content-Type` keeps its first 256 characters, and a tab keeps at most 300 records of at most this allowance of address characters together (300 × 8192 ≈ 2.4 Mi, so that part is never reached); each response looks its address up in a table, never re-reading the ones recorded |
| `LIMITS.attrLength` | 256 characters | a `<source>`'s `type` that is longer counts as absent (as with `HLS_LIMITS.attrLength`); in selector reads, each node's tag name, `id` and every class are cut to this length (the report keeps 64 characters anyway, so it is the same). Counted in the report's `limits.longValues` |
| `LIMITS.attrNames` | 32 names | in selector reads, a node keeps its first 32 attribute names (the report keeps 32 anyway); the rest are counted in `limits.longValues` |
| `LIMITS.fileTracks` | 1000 tracks | single-file tracks: first the ones any media element refers to (its `src`, `currentSrc` or a `<source>`, playing or not), then the others, each group in address order; the rest are not listed. Only a page past the limit sees a difference; the 8 probes for size and type are as before |
| `MAX_MANIFEST_URL_LENGTH` (`detect.js`) | 8192 characters | a manifest with a longer address is skipped unread (`LIMITS.urlLength` has already taken it out) |
| `MAX_MANIFEST_BYTES` (`src/lib/bgfetch.js`) | 2 MiB | a manifest is read this far; more counts as a failed read |
| `HLS_LIMITS` (`src/lib/hls.js`) | 256 variants, 256 renditions, 30000 segments, 256 `#EXT-X-MAP`, 4096-character addresses, 16 Mi characters per playlist | the rest is left out, quietly |
| `HLS_LIMITS.attrLength` | 256 characters | attribute values a track keeps (`CODECS`, `NAME`, `LANGUAGE`, `GROUP-ID`, `CHANNELS`, and with them `AUDIO`, `VIDEO`). A longer one counts as absent, not cut: half a codec list or a name would look real |
| `TEMPLATE_LIMITS` (`src/lib/dash.js`) | 14 entries, see the source; 16 Mi characters per MPD | likewise |
| `TEMPLATE_LIMITS.attrLength` | 256 characters | a longer `codecs` or Representation `id` counts as absent (a Representation's own over-long `codecs` does not fall back to the AdaptationSet's); an AdaptationSet with a longer `lang` is not offered as a track, because `lang` is part of the track's selector, which LectureFlow matches against the MPD as it is |
| `MAX_TESTS_PER_RULE` (`src/lib/profile.js`) | 256 addresses per track rule | other tracks are not tested against that rule |

### After detection: what the background keeps, what a card shows (`RETAIN_LIMITS`, `src/lib/retain.js`)

Detection results live in memory only: one for each tab's top-level detection, one for each in-page button's (embedded frame's; at most `frameResults` a tab). They are dropped when the tab closes or moves to another address, and go when the browser unloads the extension's background (Chrome's service worker, Firefox's event page, when idle).

| Constant | Value | What it does, and past it |
|---|---|---|
| `tracksShown` | 200 tracks | the popup, the in-page card and the confirmation window list at most this many. First the tracks the three choices (Main audio and video / Two cameras / Audio only) pick from all tracks, then the others in list order; the rest are not listed, cannot be ticked and cannot be sent, and the list says how many it left out (`tracksHidden`). The count in the header, the protected count and the toolbar badge still count all tracks. "Allow reading cookies" offers only the hosts of the shown tracks |
| `tracksKept` | 1000 tracks | tracks the background keeps at all, picked the same way (the shown ones first, so the tracks shown and sendable are exactly those without the limit); the rest are given up and counted in "N more not shown"; the header and the badge still count all tracks. The exported report gives the number in `limits.tracks` (a replay of such a report finds more tracks than `expected` lists) |
| `textChars` | 512 Ki characters | the longest manifest text the detection report takes (the same value in `src/lib/report.js`). A longer text is never in a report (`truncated`), so the background does not keep it |
| `tabTextChars` | 8 Mi characters | manifest text one tab keeps for its report, in the order it was read; what does not fit is marked `truncated` (so is it in the report). In-page button detections make no report and keep no text |
| `totalTextChars` | 32 Mi characters | all tabs together. Past it, first the other detections of the tab just stored give their texts up, then the others, largest first (of equal ones the oldest; SEC36 低-10: a few large pages cannot push out smaller tabs opened earlier), never their tracks; a report for such a tab detects again |
| `totalScanChars` | 64 Mi characters | address characters of the scans all detections keep for the report (`raw.frames`, `raw.webRequests`: frame addresses, media elements and their `<source>`s, resource entries, request records; one holds at most about 16 + 4 Mi plus the page's own address). Only a tab's top-level detection keeps its scan; in-page button detections make no report and keep none. Past it, detections give their scans up in the same order as for `totalTextChars` (the largest first), with their texts (their report detects again anyway), never their tracks |
| `frameResults` | 16 | in-page button detections one tab keeps (one per frame whose in-page card was used). Past it the oldest is forgotten: that card detects again when opened again; a card still open gets "the page has changed" on sending and has to be closed and opened again |

Characters: V8 stores ASCII-only text in one byte a character, other text in two. The three text allowances above cover **manifest text** (`fetches[].text`) only: at most about 16 MiB per tab and 64 MiB over all tabs (it used to be 40–80 MiB per tab at worst, for any number of tabs). They are not a bound on what the background keeps; these are outside them:

- **Tracks** (addresses, variants, names): the shown ones are always kept and can always be sent; with the others, at most `tracksKept`. File tracks number at most `LIMITS.fileTracks`, with addresses of at most `LIMITS.urlLength`; tracks from manifests are bounded by the per-detection limits as well (every DASH track id holds the whole manifest address, at most 8 KB).
- **The scan** (`raw.frames`, `raw.webRequests`, for the report) is the one detection worked on, already held to `LIMITS.frames` / `elements` / `sources` / `resources` / `urlLength` / `scanChars` / `requestChars` above: at most 16 Mi characters of addresses in the frames and their contents, and at most 4 Mi more in the request records (in practice at most about 2.4 Mi), plus the addresses of the frame detection runs in and of the top frame (outside the allowance and of any length; the top frame's is the tab's own address). Values observed in page responses (`observed`) have limits of their own (`src/lib/observe.js`: 2048 characters a string, at most 16 values from a `*`).
- **What detection uses only while it runs is no longer kept** (SEC33 低-3): `ignored` (the list of every non-media address) is not stored, of `segmentRuns` only each run's `count` (all the report takes), not the address templates, and of `evidence` only its four flags (`mse`, `mediaKeys`, `mediaKeysOnStream`, `encrypted`: all the report takes); the MediaKeys addresses and the elements' durations were used during detection and are not kept (SEC33 低-5). The detection function itself (and the fixture replay in the profile CI) still returns both whole.
- A `<source>`'s `type` and the nodes of selector reads (`reads`) are held to `LIMITS.attrLength` / `attrNames` (see the table); the values read are cut to 1000 characters by the scan, with at most 3 nodes a selector, 8 levels a node path and 8 classes a level.
- The addresses of unreadable embedded frames the popup suggests granting (`opaque`, at most 20): one longer than `LIMITS.urlLength` loses its `#` fragment, and is left out if still longer (counted in `limits.longUrls`); what reads them looks at host and path only.
- Over all tabs: manifest text `totalTextChars`, scans `totalScanChars`; in-page detections at most `frameResults` a tab (see the table).
- An embedded frame that moves on to another document during a top-level detection gets no more fetches and only the tracks it alone gave are left out; the rest is stored (SEC36 低-9). Known gap (低-12): addresses of other frames that a manifest from it "absorbed" as its segments go with that track.
- **Still not bound**: the addresses of the frame an in-page button detects in and of the top frame (see above; browsers allow some 2 MB; it is the page's own address, which detection, profile matching and the report all use, so it cannot be cut); tracks (at most `tracksKept` a detection, addresses as in the first point) have no total over tabs, whose number the user decides.
- Measured before → after (the author's probe, Node, one detection through "bound the scan → detect → keep the tracks → copy", what stays after GC):
  - 2000 file addresses of 8192 characters: 49.2 MiB, 196 ms → 32.6 MiB, 185 ms;
  - 4000 media elements with 8000-character addresses: 126.6 MiB, 270 ms → 31.9 MiB, 58 ms;
  - 20 frames of 2000 entries with 1000-character addresses: 146.1 MiB, 682 ms → 13.3 MiB, 147 ms;
  - 1000 addresses of 16400 characters differing only at the end: 63.9 MiB, 2486 ms → 0.2 MiB, 1 ms.
- Worst shapes (the SEC33 reviewer's probe `mem.mjs`, whole `detectTab`, after GC with the page's input freed; "before" as the SEC33 review measured it, "after" measured again by the author, C130, with the same probe once `ignored` and the segment templates were dropped and `type` / `reads` bounded):
  - 10000 distinct non-media addresses of about 16 Mi characters together: 37.4 → 20.1 MiB, no tracks;
  - the same in runs of three segments: 43.2 → 20.5 MiB;
  - 1000 elements × 16 `<source>`s with a 512-character `type`: 29.9 → 21.9 MiB (22.3 MiB with 9 characters);
  - selector-read nodes with 2048-character `id` / `classes` and 1000 attribute names each: 8.5 → 6.6 MiB (node data 4.75 → 0.46 Mi characters);
  - 1000 elements with 8192-character file addresses: 27.3 → 27.2 MiB (unchanged: 15.6 Mi characters of scan plus 7.8 Mi of file track addresses);
  - 1000 elements with MediaKeys × 16 `<source>`s of 1 Ki-character addresses (the SEC33d review's `keys` shape): 37.1 → 21.9 MiB (the 15.9 Mi characters of `mediaKeysUrls` no longer kept; measured by the author, C130, with the same probe before and after dropping it).
- From the limits: about 16 (scan) + about 2.4 (request records) + 8 (file track addresses) + 8 (DASH track ids) ≈ 35 Mi characters per tab and detection, plus the 8 Mi manifest text allowance and the selector-read nodes (at most about 28 K characters a node: 8 levels × tag, `id` and 8 classes of 256, plus 32 attribute names of 256), and the unbounded items of the previous point.
- Past any limit, the exported report has a `limits` object saying how much was left out of each (`frames`, `elements`, `sources`, `resources`, `webRequests`, `longUrls`, `scanChars`, `longValues`, `fileTracks`, `tracks`); within all of them there is no such object and the report is as before.
- **Lecture details fetched for an in-page list** (`sessions` in `main.js`) expire after 30 minutes (checked when read) and have no count limit; each holds a few named tracks made of observed values, and their number grows with the user's bulk sends: at most 500 rows a batch from the confirmation window, while the in-page bulk card loads lecture by lecture with no such limit.

Before storing, the background copies the detection (`detachedCopy`): a string a parser took out of a manifest (a `CODECS` value, say) can share the whole text's memory in V8, and would keep a text that was given up alive. The copy is **deduplicated by string**: a string is copied once however many places hold it, and objects that were shared stay shared. Strings longer than 16383 characters (`DEDUP_MAX_LENGTH`) are the exception: V8 hashes such a string by its length only, so many long strings of one length would make the table compare them one by one (SEC28b 中-3); they are copied at every place instead. `structuredClone` writes one copy per reference, so a value shared by 2000 Representations became 2000 copies (SEC28 高-1). Its time and extra memory grow with the total length of the distinct strings plus the number of objects: the worst shape (every string distinct, 3072 tracks, 30 Mi characters) took 106 ms, the copy itself about 55 MiB.
